# Bugfix Requirements Document

## Introduction

Previewing a large PDF in the Note-Sphere viewer is slow on mobile. For a large
document (e.g. a 239-page file), the first page can take roughly 10 seconds to
appear over a slow mobile connection.

The delay is caused by two behaviors in the PDF viewer:

1. **Whole-file eager download.** `components/modals/PDFDocument.tsx` renders the
   react-pdf `<Document file={{ url }}>` component **without any pdf.js
   `options`**. pdf.js defaults to `disableAutoFetch: false`, so it eagerly
   downloads the **entire** PDF (all 239 pages) before/while rendering page 1,
   even though only a single page is displayed at a time
   (`<Page pageNumber={currentPage} />`). On slow mobile links, this whole-file
   transfer dominates the time-to-first-page.

2. **Forced high-DPI rendering.** The `<Page>` uses
   `devicePixelRatio={Math.max(window.devicePixelRatio, 2)}`, forcing 2x–3x canvas
   rendering on high-DPI phones and adding avoidable work to the first paint.

The presigned URL served to the viewer is generated by
`app/api/notes/[id]/route.ts` (GET) via `lib/s3.ts` `getPresignedUrl`
(S3 `GetObject`, `expiresIn: 3600`). S3 supports HTTP Range requests, so pdf.js
can fetch only the bytes for the current page — but only if the S3 bucket CORS
configuration exposes the range-related headers (`Accept-Ranges`,
`Content-Range`, `Content-Length`, `ETag`) to the cross-origin browser.

The fix enables pdf.js lazy/partial (range-request) loading, caps render
resolution on high-DPI devices, and documents the required S3 CORS
configuration — while preserving every existing viewer feature.

**Note:** Measurable time-to-first-page improvement depends on the S3 bucket CORS
configuration exposing the range headers listed above; without those headers the
browser cannot use HTTP Range requests cross-origin.

## Bug Analysis

### Current Behavior (Defect)

What currently happens when a large PDF is previewed, especially on mobile:

1.1 WHEN a PDF is opened in the viewer (`PDFPreviewModal` → `PDFDocument`) THEN the system renders `<Document file={{ url }}>` with no pdf.js `options`, leaving `disableAutoFetch: false`, so pdf.js eagerly downloads the entire file (all pages) before/while showing page 1.

1.2 WHEN a large PDF (e.g. a 239-page file) is previewed over a slow mobile connection THEN the system takes ~10 seconds to display the first page because the whole-file download dominates load time, even though only one page is shown at a time.

1.3 WHEN a page is rendered on a high-DPI mobile device THEN the system uses `devicePixelRatio = Math.max(window.devicePixelRatio, 2)`, forcing 2x–3x canvas rendering and adding avoidable render cost to the first paint.

### Expected Behavior (Correct)

What should happen instead for the same conditions:

2.1 WHEN a PDF is opened in the viewer THEN the system SHALL pass a stable pdf.js `options` object to `<Document>` with `disableAutoFetch: true`, `disableStream: false`, and a `rangeChunkSize` (e.g. `65536`), so only the bytes needed for the current page are fetched via HTTP Range requests instead of the whole file.

2.2 WHEN a large PDF (e.g. a 239-page file) is previewed over a slow mobile connection AND the S3 bucket CORS exposes the required range headers THEN the system SHALL display the first page substantially faster than the whole-file download baseline, because only the first page's byte range is fetched initially.

2.3 WHEN a page is rendered on a high-DPI mobile device THEN the system SHALL cap render resolution using `devicePixelRatio = Math.min(window.devicePixelRatio || 1, 2)` to reduce first-paint work while staying visually crisp.

2.4 WHEN react-pdf re-renders `PDFDocument` without a change to the document source THEN the system SHALL keep the `options` object identity stable (module-level constant) so the document is not reloaded.

2.5 WHEN a developer configures the deployment THEN the system SHALL document the required AWS S3 bucket CORS configuration (`ExposeHeaders`: `Accept-Ranges`, `Content-Range`, `Content-Length`, `ETag`; `AllowedMethods`: `GET`, `HEAD`) in the README, since HTTP Range requests only take effect when the browser can read those headers cross-origin.

### Unchanged Behavior (Regression Prevention)

Existing viewer behavior that must be preserved (inputs where the bug condition does not apply):

3.1 WHEN a user creates or edits highlight, scribble, or eraser annotations THEN the system SHALL CONTINUE TO create, render, and persist those annotations exactly as before.

3.2 WHEN a user selects text in the rendered page THEN the system SHALL CONTINUE TO support text-layer selection.

3.3 WHEN a user zooms in or out THEN the system SHALL CONTINUE TO scale the page correctly across the existing zoom range.

3.4 WHEN a user navigates pages (previous, next, or jump-to-page) THEN the system SHALL CONTINUE TO display the requested page, fetching that page's data on demand (on-demand per-page fetching is acceptable and desired).

3.5 WHEN a user reverts annotations THEN the system SHALL CONTINUE TO revert as before.

3.6 WHEN a PDF is previewed from the dashboard or from a public share page THEN the system SHALL CONTINUE TO load and render correctly with all existing viewer features intact.

3.7 WHEN the `PDFPreviewModal` obtains a presigned URL (fetched internally via `GET /api/notes/[id]` or supplied via the `presignedUrl` prop) THEN the system SHALL CONTINUE TO use that URL to load the document as before.

## Bug Condition Derivation

**Bug Condition Function** — identifies inputs that trigger the slow first-page load:

```pascal
FUNCTION isBugCondition(X)
  INPUT: X of type PdfPreviewRequest  // { url, pageCount, connection, devicePixelRatio }
  OUTPUT: boolean

  // The viewer eagerly downloads the whole file and/or over-renders on high DPI,
  // making the first page slow to appear.
  RETURN previewOpened(X)
         AND documentOptions(X) = NONE            // no pdf.js options => disableAutoFetch:false
         // OR forced high-DPI over-rendering on the first paint
         OR renderDevicePixelRatio(X) = max(window.devicePixelRatio, 2)
END FUNCTION
```

**Property (Fix Checking)** — desired behavior for buggy inputs:

```pascal
// Property: Fix Checking - Fast first page via lazy range loading + capped DPI
FOR ALL X WHERE isBugCondition(X) DO
  result <- renderPreview'(X)   // fixed viewer
  ASSERT documentOptions(result).disableAutoFetch = TRUE
     AND documentOptions(result).disableStream = FALSE
     AND documentOptions(result).rangeChunkSize > 0
     AND renderDevicePixelRatio(result) = min(window.devicePixelRatio OR 1, 2)
     AND onlyCurrentPageBytesFetchedInitially(result)   // given S3 CORS exposes range headers
END FOR
```

**Preservation (Preservation Checking)** — behavior for non-buggy inputs:

```pascal
// Property: Preservation Checking
FOR ALL X WHERE NOT isBugCondition(X) DO
  ASSERT renderPreview(X) = renderPreview'(X)   // F(X) = F'(X)
END FOR
```

Where **F** is the current (unfixed) viewer and **F'** is the fixed viewer. All
viewer features not related to document fetching / DPI — annotations, text
selection, zoom, page navigation, revert, and dashboard/share-page behavior —
must remain identical.
